# 09: 稳定性与验收

**What to build:** 连续陪看整片（84.7 分钟）不崩、不涨内存、延迟落在门槛内。这一票不做新功能，只把前面七票拼起来证明它能长时间工作。**时长口径 2026-11-22 由「两小时」改为「全片 84.7 分钟」，理由与代价见 Comments。**

**Blocked by:** 03, 04, 05, 06, 07, 08

**Status:** claimed（2026-11-22 改为两阶段：先 30 分钟冒烟找问题，通过后从头重跑、连续跑满全片 84.7 分钟）

## 阶段 A：30 分钟冒烟（**不是验收**，只为找问题）

- [ ] 连续跑 30 分钟，`state` 全程 `running`，事件 id 无断号
- [ ] 出问题**当场修**，修完从头重来；这一轮的任何数字都不计入验收
- [ ] 结束时确认三个通道都在出东西（motion / ocr / speech 各 ≥ 1 条）

## 阶段 B：全片（84.7 分钟）连续跑（**这一轮才算验收**）

- [ ] 从头开始放，**连续跑满全片 84.7 分钟**不崩溃，内存不持续上涨（首尾差 < 15%）
- [ ] 画面事件延迟：普通变化 < 400 ms，切镜 < 1 s
- [ ] 字幕延迟 < 2 s；声音延迟（3 秒句）< 1 s
- [ ] 单张拼图 token ≤ 250
- [ ] 8 fps 区域采集时 CPU 占用 < 0.2 核
- [ ] 全程内发生一次故障注入（关窗口/杀 OCR），系统按票 06 的语义处理且可恢复
- [ ] 事件队列在跑满全片后仍能正确返回 `sinceId` 语义（无重复、无跳号）
- [ ] python 两个服务（OCR/ASR）的 RSS 另采一份 —— `soak.mjs` 不覆盖它们

## 压测脚本（2026-11-21 10:01）

```
node scripts/soak.mjs "窗口标题片段" 120
```

只验三件事：**不崩**（state 一直 running）、**不丢**（事件 id 连续，断号即报）、**不涨**（RSS 首尾 5 次采样均值，涨超 50% 判失败）。

实跑 1 分钟先验脚本本身：`frames=478`、`RSS 61MB 平稳`、verdict 通过。
两小时那轮还没跑——需要人挂着。

**已知不覆盖**：python 两个服务（OCR/ASR）的长时间稳定性不在这个脚本里，
要另开终端看它们的 RSS，或者以后把它俩也纳入采样。

## 实跑：40 分钟（2026-11-21 10:49，中途 Ctrl+C）

| 指标 | 数值 | 判定 |
|---|---|---|
| 帧率 | 8.27 fps（目标 8） | ✅ |
| 崩溃 | 无，state 全程 running | ✅ |
| 事件 | 212 条 / 40 分钟 = **5.4 条/分钟** | ⚠️ 超 spec 上限 4 |
| RSS | 首 5 次均 93MB → 末 5 次均 114MB，峰值 148MB，斜率 **0.54 MB/分钟** | ⚠️ 温和上升，两小时预计 +60MB |

**结论**：稳定性初步通过（没崩、帧率准），但两件事要跟进：

1. **密度超上限**（5.4 > 4 条/分钟）→ 转票 10（那里已记录“浏览器视频 7 条/分钟”）
2. **RSS 斜率 0.5MB/分钟**：不算泄漏（没有单调暴涨，峰值后回落），但两小时会到 150MB 上下。
   要判死是否泄漏，得跑满并看**末段斜率是否趋零**——现在只有 40 分钟，趋势还看不清

**没验到的**：事件断号（`gaps`）——Ctrl+C 跳过了 summary。已给脚本加 SIGINT 处理，下次中断也会出结论。

## Comments

### 2026-11-22 计划变更：从「两小时」改成「30 分钟冒烟 + 全片 84.7 分钟」

**票面原文写的是「连续运行 2 小时」。现在改成 84.7 分钟，这是用户决定的，理由如下：**

- 片子《反向之地合集（1-6）》窗口标题写「时长2小时半」，但**字幕真值只覆盖 84.7 分钟**
  （实测真值文件 1553 条、0 → 84.7 分钟）。用户要跑的是"整片放完"，也就是 84.7 分钟。
- 这条时长变更是**打了折的**，不是"2 小时已验证"：B 阶段跑满 84.7 分钟就是这一轮的上限，
  别在别处写成"两小时稳定性已通过"。

**结构改成两段（关键：只有 B 段算验收）：**

| 段 | 时长 | 目的 | 计入验收 |
|---|---|---|---|
| A 冒烟 | 30 分钟 | 只为找问题，出问题当场修、修完从头重来 | ❌ |
| B 正式 | 84.7 分钟（全片） | 这一轮的数据才算 | ✅ |

**为什么不能拆成两段正式跑**（2026-11-22 曾提过 24 + 60 的方案，已否掉）：断号、
RSS 斜率、事件 id 连续性三项都只在**同一次会话**内成立。拆开等于把这张票最核心的
三项全废掉。

**执行时必须同时满足（否则数据作废）：**

1. **屏幕常亮、不锁屏** —— BitBlt 抓的是屏幕像素，锁屏后抓到的是黑的，后段全废；
2. **目标窗口不被遮挡、不最小化** —— 被盖住就开始读别人的字；
3. **票 11（主动唤醒）保持默认关** —— 它会往会话塞消息、多跑一轮模型，直接污染 CPU / RSS 曲线；
4. **另开一个窗口跑 `scripts/monitor-resources.py`** —— `soak.mjs` 只采 Node 侧，python 两个服务不在里面。
