
只验三件事：**不崩**（state 一直 running）、**不丢**（事件 id 连续，断号即报）、**不涨**（RSS 首尾 5 次采样均值，涨超 50% 判失败）。

   要判死是否泄漏，得跑满并看**末段斜率是否趋零**——现在只有 40 分钟，趋势还看不清

**没验到的**：事件断号（`gaps`）——Ctrl+C 跳过了 summary。已给脚本加 SIGINT 处理，下次中断也会出结论。

### 延迟的真实构成（2026-11-23 拆分）

- **字幕**：攒批 1.6 s（batch=3 × 800 ms）+ 推理 2.3–2.8 s + 排队 0–2.5 s
- **声音**：拉取窗口 3 s + 句尾余量 0.8 s + 推理 1–2 s
- 之前测到的 "事件比字幕晚 5–16 s" 里混着**按播放到点 watch_start 的错位**，不是纯延迟；
  已加 `latencyMs` 埋点（`caa99a3`）。

**实测（2026-11-23 06:45–06:51，5 分 49 秒那轮，`latencyMs` 口径）**：

```
延迟 OCR 2.6/4.1s ｜ ASR 3.6/4.7s（p50/p90）
```

两条都远低于改后的口径（≤7 s / ≤8 s）。**原写的 <2 s / <1 s 确认不可达**：单次 OCR 推理
2.3–2.8 s，ASR 光拉取窗口就 3 s。**这一条以实测为准，不再按拍脑袋的门槛判。**

### 期间修掉的两个真 bug

1. **ASR 时间轴漂移**：`asrFirst` 只在进程生命周期里重置一次，第二场接着上一场跑；
   且时间用"样本数 ÷ 采样率"，录音抖动让游标跑到 1.14 倍。修法：每场 reset + 墙上时钟锚点。
   90 分钟实测比值 **0.997**（修前 1.14）。
2. **OCR 吞吐**：单路串行只能读 17 次/分钟，追不上 23 条/分钟的字幕。改 batch=3（帧间隔 800 ms）
   + scale=1，吞吐到 ~27 次/分钟，逐句覆盖率 29% → 65–77%。
