# 10: 事件密度与尖峰扳机标定

**What to build:** 画面一直在动时（视频播放），30 秒只出 1 条事件，太稀疏；但也不能每帧都报。这一票只调密度，不改判据，改完 AI 拿到的事件节奏应当接近人说话的节奏。

**Blocked by:** 02

**Status:** ready-for-agent

- [x] 已有标定数据（票 02 实测）：
  - 真视频播放：帧间 `moved = 15.7% / 69.2% / 24.1% / 25.1%`
  - 静止界面：`moved = 0.01% – 0.07%`
  - **差三个数量级**，所以原来拍的阈值 6 毫无意义
- [ ] 用 `moved` 的真实分布定扳机阈值（不是拍数），并把阈值写进配置而不是代码
- [ ] 目标：30 秒内 2–6 条 `motion`（对应"每 5–15 秒一条"）
- [ ] 反向验收：静止画面仍然 0 条（加大密度不能以刷屏为代价）
- [ ] 区分「视频在播」与「镜头切换」：目前两者都产出 `cut=true`，需要至少一条能分开的量（候选：切点前后的帧相似度突变 vs 持续小变化）

**不要做的事**

- 不要为了让 `motion` 变多而调低 pipeline 的切点阈值 —— 那会改变「什么算变化」的定义，属于另一件事
- 不要用 `peak` 做判据（region 模式下它被 `toFixed(1)` 抹成 0，票 02 已经踩过）

## 结论（2026-11-21 08:49）：不调参，关闭此票

先核对了 spec 自己的目标：**游戏 4 条/分钟、影视 3 条/分钟**，且上限是"不多于 4 条"。

实测：60 秒 1 条 `motion`（`cut=true`，`from 0 → to 20.38`），也就是约 **1 条/分钟**——
低于目标，但**没超上限**，而且那 60 秒的视频里确实只有一次明显切换。

**所以不是"太稀"，是"那分钟没发生多少事"。** 再加密只能靠调低判据，那会让事件不再对应真实变化——
这正是 spec 里"连续运动不会几十条/分钟"要防的东西。

### 保留的结论
- `maxWaitSec = 15` 决定了密度上限（最多 4 条/分钟），与 spec 目标一致
- 尖峰扳机保持关闭（`spikeThreshold = 0`）；它的阈值在真实素材上仍无标定依据，
  开着只会把批次切碎（实测 `cells=2`、`where` 为空）
- 真要提速，正确方向是**降低 `maxWaitSec`**（8 秒 → 最多 7.5 条/分钟，会超目标），
  或按场景预设分档 —— 这是产品决定，不是 bug 修复
