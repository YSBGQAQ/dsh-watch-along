# DSH 插件生态里做实时听写 / 系统声音转写的方案有哪些？

调研日期：2026-11-22

> 范围：DeepSeek Harness（DSH）官方仓库源码、插件 README／一手商店页、作者说明。所有联网检索走 search MCP（`anysearch` + `fetch(render:"http")`），逐条 claim 指向实际打开过的 URL 或本地一手源码路径。本地 `vendor/` 与桌面四个只读 zip 为交叉验证用一手源码。**未穷尽**：`deepseekdocs.com/en/ecosystem` 声明 1382 个项目、页面只展示前 60，`dsh-external/hub` 与 awesome list 未遍历。

## 结论

1. `docs/reference-projects.md:176` 的「四家都不抓系统声音」**只对 better-ears / soundtry / hear / qian-music 这四个喂文件分析器成立**；放大到整个 DSH 生态，这个判断**不成立**。至少有 5 个插件抓系统输出（WASAPI loopback），其中 3 个是「系统正在播什么就实时转写」：本项目 vendor 里的 `dsh-see-now`（`listen.py` + `src/listen.js`）、`Oreo0614/dsh-realtime-subtitles`、`drliuhuan/dsh-plugin-live-meeting`。
2. 因此本项目「**唯一**做系统正在播什么就实时转写」的说法**不成立**。`Oreo0614/dsh-realtime-subtitles` 的方案（`WASAPI loopback → WebRTC VAD → faster-whisper tiny/base → 滚动字幕`，CPU、本地）与本项目几乎同构，差别主要在本项目用 `large-v3-turbo(GPU)` 且输出为「事件流进 agent 上下文」而非给人看的字幕。
3. 生态里数量最多的是**麦克风实时听写**（`getUserMedia` / `MediaRecorder` / `AudioWorklet` / Web Speech API），它们「边说边出字」但抓的是麦克风，**不是系统输出**。宿主自带的 `speechToText` 服务是官方 `speech-to-text-sensevoice` provider（SenseVoiceSmall ONNX + Silero VAD，Host CPU，零部署），形态是**录完一段再提交转写**（record-then-transcribe），不是实时流式。
4. 「loopback」一词在生态里被混用：多数指**网络 loopback（127.0.0.1 本机 HTTP）**（宿主 speech-to-text 的 "Authenticated loopback requests"、Qwen provider、模型下载端点、测试用 "fake loopback provider"），**只有极少数指 WASAPI 音频环回**。核验第 176 行判断时这是一个必须拆开的歧义。
5. `dsh-watch-together`（SAOS-3624，与 see-now 同作者）是「陪看 + 分镜 + 字幕/离线 ASR 时间码」，**不是**实时系统环回转写；其公开仓库 `floating-chat/` 不含 `listen.py`／`procloopback.py`。see-now README:772 的「两边现在是同一个协议」是**许可证（Apache-2.0）语境**，不是实时听写线协议——此点与 team-lead 的初始解读有出入，详见「未解决 / 存疑」。

## 发现

### A. 宿主自带的 speechToText 服务与官方语音输入（问题 1「特别留意」项）

- 官方 provider `deepseek-ai/dsh-experimental-speech-to-text-sensevoice`：`SenseVoiceSmall ONNX + Silero VAD` 跑在 **Host CPU**，用平台相关 `sherpa-onnx` Node 包，「no Python, compiler or model conversion」；`precision=int8` 默认，INT8 权重约 **239 MB**、FP32 约 938 MB；语言 hint 支持 auto／中／英／粤／日／韩；「CPU only」。 — [GitHub 官方 monorepo README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/speech-to-text-sensevoice/README.md)（抓取于 2026-11-22）
- 该 provider 是**整段录音提交、非实时流式**：README 写「One managed Node subprocess serializes inference. **Recordings submitted during wake-up join the bounded queue**」「Transcription never starts preparation downloads」「**Authenticated loopback requests keep audio in memory**」——这里的 loopback 是本机 HTTP 回环，不是 WASAPI 音频环回。 — [同上](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/speech-to-text-sensevoice/README.md)（抓取于 2026-11-22）
- dsh 0.2 自带实验性语音输入 bundle `@deepseek-ai/dsh-experimental-voice-input-bundle`（local SenseVoice），**默认关闭**，且是「record-then-transcribe：click the microphone, speak, click Stop, and the transcript is inserted into the draft」。 — [tonyd2wild/DeepSeek-Harness-Dictation README](https://github.com/tonyd2wild/DeepSeek-Harness-Dictation)（抓取于 2026-11-22）
- 官方 issue 层面尚无内置语音输入：Discussion #5049 是「Add a built-in voice input (speech-to-text dictation) option to the DSH Web UI」的 feature request，回复讨论的是「Host-owned STT provider contract」「explicit non-persistence by default」，并明确其证据「used synthetic Web Audio and a **fake loopback provider**; it is **not** physical-device, live-provider, or packaged-Desktop proof」。 — [deepseek-ai/deepseek-harness Discussion #5049](https://github.com/deepseek-ai/deepseek-harness/discussions/5049)（抓取于 2026-11-22）
- 该 provider registry 可被第三方替换：`m-eang/dsh-stt-qwen` 把识别器换成本地 CPU 的 `Qwen3-ASR-0.6B`（可选 1.7B），「hooks into the official speech-to-text provider registry without touching official code」「all traffic staying on 127.0.0.1」；仍是麦克风录音→草稿。 — [dsh-plugin.org 商店页（独立改写，作线索）](https://dsh-plugin.org/plugins/m-eang/dsh-stt-qwen)（抓取于 2026-11-22）
- 多个插件复用／依赖这份宿主能力，交叉印证它确实存在：`better-ears` 三级降级第 1 档「DSH 里已经有 `speechToText` 服务…直接用它，模型本来就是本地 SenseVoice」（本地 `dsh-better-ears-main/README.md:58`）；`anchoredship/dsh-audio-transcribe` 「reuses the SenseVoice cache that DSH's own voice input already prepared」，缓存路径 `<dshHome>/speech-to-text/sensevoice/models`；`drliuhuan/dsh-plugin-live-meeting` 要求「official Voice Input bundle enabled」。 — [anchoredship README](https://github.com/Anchoredship/dsh-audio-transcribe)、[drliuhuan README](https://github.com/drliuhuan/dsh-plugin-meeting)（抓取于 2026-11-22）

## 与本项目对比

本项目定案（`docs/adr/0003-audio-turbo-only.md`）：**WASAPI 环回 → VAD → faster-whisper large-v3-turbo(GPU) → 事件流**，明确「不做 MDX 人声分离，不保留 SenseVoice 作快档」「GPU 依赖缺失时显式报错，不许静默变成没有字幕」。

**可以借鉴（与实时环回前提相容）**

- **时间码用 epoch 毫秒、不用样本数累加**：see-now `listen.py:24-25, :279, :358-360` 与本项目 ADR 0003:9 已一致（「WASAPI 静音时不推数据，样本计时会永久漂移」）；`anchoredship` 也踩了「静音不推数据 + `Read` 阻塞」的坑。可继续复用 `seg-<epochMs>.wav` 命名。
- **进程级环回**：see-now `procloopback.py` 已实现 `ActivateAudioInterfaceAsync` + `INCLUDE_TARGET_PROCESS_TREE`，能从源头把 AI 自己的 TTS 排除，比本项目现有「整机环回 + quiet-until 装聋」更干净。本项目票 17 尚未做，这是最值得直接搬的一块（纯 ctypes、零依赖）。
- **先混单声道再降采样的顺序**（`listen.py:27-28`：「顺序错了会相位抵消、ASR 只认出『嗯。』」）、**静音补 -120dB 时间格**（`:358-360`）、**长句先出临时版再被终版覆盖**（`:413-415`、`Oreo0614` 的 tiny 草稿 / base 定稿双模型）——都是降低感知延迟且不依赖 GPU 的手段。
- **幻觉与自听处理**：see-now 的 `quiet-until.json`（`:450-452`）、`better-ears` 的 `lib/asr.js:26` 中英幻觉词表 + `looks_hallucinated()` 正则、无人声不送识别器——本项目 ADR 0003 已承认「BGM 压过人声会掉字、唱歌会被当说话」，这些过滤层是低成本补丁。
- **降级链 / 零部署**：`better-ears` 的 host/http/command 三级、see-now 的三级降级、`GooDAnDReaDY` 的多 provider fallback chain。**尤其是宿主 `speechToText`（SenseVoice，CPU，零部署）**，见下一节。

**不能照搬（因「实时环回」前提不成立或不匹配）**

- **浏览器 `getUserMedia` / `MediaRecorder` / `AudioWorklet` / Web Speech API 那一整套**：抓的是麦克风 capture endpoint，抓不到系统输出。`dsh-pinpu` 作者实测本机「立体声混音」被禁用、`navigator.mediaDevices` 根本不列出；`Jstn-1g` 的 "fake loopback provider" 与 127.0.0.1 是网络回环，不是音频环回。生态里绝大多数「实时听写」插件属此类，对本项目的采集层没有可复用代码。
- **喂文件 CLI / 按窗口切**（soundtry 的 `argparse` + `--input/--start/--end`、anchoredship 的「录完 WAV 再 auto-transcribe」、qian-music 的「下载音视频交 Omni」）：实时流没有「文件结束」这个信号，VAD 段是持续产生的，需要长驻 worker 而非每次重启 Python（`reference-projects.md:193` 已指出 soundtry 是 CLI 不是服务）。
- **dsh-watch-together 的播放位置驱动**：靠浏览器扩展报 `currentTime` + yt-dlp 字幕轨 + 分镜预取，是「跟着播放进度交付」，与「系统正在播什么就实时转写」是两种时钟模型；且它依赖 cookies/扩展，本项目要求音频不离机、无外部依赖。
- **云 ASR**（DashScope / Volcengine / Deepgram / Groq / Qwen realtime）：本项目定案是本地 GPU turbo + 音频不出机器。
- **输出形态**：字幕浮层（oreo0614）、会议纪要 + 说话人（drliuhuan）、composer 草稿（麦克风听写类）都是「给人看」；本项目要的是**事件流进 agent 上下文**（`reference-projects.md:124` 的事件队列 + 长轮询 + id 高水位线）。可借事件格式，不能借交付语义。
- **MDX/Demucs 人声分离**：ADR 0003 已按「主场景是游戏直播、主播说话占主导」砍掉，oreo0614/drliuhuan 也都没做分离；保留为「开关，不是地基」的判断仍成立。

## 与 see-now 实时听写对标

`dsh-see-now` 的 `examples/floating-chat/listen.py` + `src/listen.js` 是**与本项目直接对标的完整实时环回转写链**，且已在 vendor 里有全量源码：

| 环节 | see-now 现成方案 | 本项目 ADR 0003 |
|---|---|---|
| 采集 | `pyaudiowpatch` WASAPI loopback，支持设备/进程/auto 三档，进程级环回已实现 | WASAPI 环回（整机）+ VAD |
| 断句 | 能量 VAD + wall-clock 静音判定（350ms），`seg-<epochMs>.wav` / `live-<t0>.wav` 临时版 | VAD（复用 better-ears `voiceBlocks()`） |
| ASR | **宿主 `speechToText`（桌面版自带 SenseVoice）** → 退 `~/.dsh/asr.json` OpenAI 兼容（默认 `paraformer-zh-2024-03-09`）→ 都没有则不出字幕 | **仅** faster-whisper `large-v3-turbo`（GPU），无快档、无降级 |
| 实测 | 抓回环 0.3% 单核；转写 1s 段 99ms / 3s 段 174ms（130–160ms）；端到端约 **0.6s** | `reference-projects.md:193` 估端到端 2–2.5s、磁盘 ~2.4GB |
| 部署 | 零部署（宿主自带）+ `pip install pyaudiowpatch numpy` | GPU + cuBLAS/cuDNN，缺失即「显式报错，不许静默变成没有字幕」 |

**要点：ADR 0003 选 turbo 单链时，实际上把 see-now 现成的「宿主 SenseVoice / 本地 paraformer + 130–160ms 转写 + 零部署 + 纯 CPU + 三级降级」这条更轻、更鲁棒的链放弃了。** `reference-projects.md:195-201` 原本定的是「SenseVoice-Small 与 turbo **双常驻** + 完整降级链（turbo→SenseVoice→无字幕）」，ADR 0003 把它简化成「只留 turbo、不保留 SenseVoice 作快档、GPU 缺失就报错」。

值得重新评估的点（不改动生产代码，仅记录）：如果主场景是陪看/游戏直播而非追求字错率下限，see-now 的 0.6s 端到端、0.3% 单核、零部署、宿主自带服务，在「延迟」和「可用性」两项上都优于 turbo 单链；至少在 GPU/cuBLAS/cuDNN 缺失时，退回宿主 SenseVoice 是生态里已验证的现成路径，比「显式报错、没有字幕」对用户更友好。反过来说，本项目保留 turbo 的理由（BGM 场景质量上限、中文长句准确率、`condition_on_previous_text=False` 防复读）在 see-now 与 oreo0614 的 README 里都没有对应实测数据支撑——两边是不同取舍，不是「谁对谁错」。
