# 陪看实测数据（截至 2026-11-23 08:20）

这份文件只干一件事：**把每一次真机跑出来的数记下来**，包括版本演进过程中变好/变坏的过程。
工单负责"该做什么"，这里负责"做出来实际是多少"。

## 怎么量

- 每一场 `watch_stop` 会打一行 `[会话汇总]`，每 5 分钟还会打一行 `[会话快照 5min]`
- 延迟（`OCR 1.2/1.4s`）是 **p50/p90**，口径是 `latencyMs`：抓到帧/音频 → 事件发出
  （2026-11-23 加的埋点 `caa99a3`；之前那段"5–16 秒"混着按播放到点的起点错位，不可用）
- 帧数、事件数、丢号（`id 1→N 缺 0`）都来自事件队列本身
- 外部指标（轮数/步数/TTFT/费用）来自 DSH 面板，手抄进来

## 已知的口径坑（读数据前先看这几条）

1. **"取帧 N 次"只数工具调用**。消息里附的图不算——2026-11-23 08:10 那轮看着"只取一帧"，
   其实是 33 张附图没记账。汇总里现在单列 `附图 N`。
2. **`会话汇总` 可能打两次**。第二次是"刚开就停"，统计已清零，会出现"帧 0、拼图 0"。
   现在这种空汇总不再打印。
3. **OCR 密度会随吞吐变**：p50 从 2.6s 降到 1.2s 后，同一份字幕被更及时地读到，
   密度从 21 条/分涨到 40 条/分——这不是阈值变松，是漏得少了。
4. **帧数 ÷ 时长 ≈ 12fps**（798×450）。帧数是采集线程的总产出，不是"模型看到几张"。
