# 0005 采集改用 koffi 直抓（放弃 ffmpeg 子进程）

日期：2026-11-21
状态：已决定，待实施

## 背景

原方案按 ADR 0001 整套复用 see-now，采集跟着它用 `spawn ffmpeg`（gdigrab）。
实测暴露两件事：

1. **DPI 不对**：ffmpeg 子进程默认不声明 DPI 感知，`lookupWindow` 给的矩形（逻辑像素）
   直接传给 gdigrab 会抓偏。同一天为换算方向错了两次（该乘 1.5、又改回除），
   三次抓取全部落空或抓到隔壁窗口。
2. **窗口匹配不可靠**：`"反向之地"` 这个片段同时命中浏览器和命令行窗口
   （命令行标题里含我们的参数），静默抓错。

streamvision 走的是另一条：进程内 `koffi` + `SetProcessDpiAwarenessContext(-4)` + `BitBlt`。
实测移植后：窗口矩形 `x=1228` 正好是 `819 × 1.5`（物理像素），**一次就抓对**，
OCR 整句读对（`就咱们一个宿舍顶着17级台风打牌确实有点爽啊`，含 `17级`）。

## 决定

**采集全部换成 koffi 直抓，不留 ffmpeg 兜底**（用户 2026-11-21 决定）。

## 取舍

| | koffi | ffmpeg |
|---|---|---|
| 坐标 | **天然物理像素** | 要自己换算（已错两次） |
| 依赖 | koffi（streamvision 自带） | 要装 ffmpeg |
| 速度 | 进程内，无 spawn | 每帧 spawn |
| 崩溃风险 | **传错参数会段错误**（已踩一次） | 子进程挂了不影响主进程 |

**代价明确**：koffi 是 native 调用，参数类型写错会**直接段错误**（`windowRect(hwnd)`
传成 hwnd 而不是标题就崩了）。所以调用点必须有测试覆盖。

## 已知不解决

**遮挡**：BitBlt 抓的仍是屏幕像素，别家窗口盖在上面就抓到它。
用户决定接受（写进 README 已知限制）。

## 替代方案（未采用）

WGC / PrintWindow：能抓被遮挡的窗口内容，但要 WinRT 互操作，参考项目无人使用，
成本远高于收益。

## 三带与门限（照抄 streamvision）

```js
BANDS = [
  { name:'top',    lo:0.00, hi:0.38, scale:2 },
  { name:'mid',    lo:0.32, hi:0.72, scale:2 },
  { name:'bottom', lo:0.66, hi:1.00, scale:3 },
]
STABLE_MS = 1200   SIMILAR = 0.85
```

带之间**故意重叠**（0.38/0.32、0.72/0.66），避免正好压在分界线上的字被切断。

**放大改为按带宽度自适应**：带宽 < 1200px 才放大到对应 scale，否则原尺寸。
理由：放大是为"字太小读不出"；4K 屏上 bottom 带 2981px 宽，
照抄 3× 会变成 8943px（约 1300 万像素），单次 OCR 从 200ms 涨到 1–2 秒，收益为零。
